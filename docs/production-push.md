# Production phone notifications

Production push support is available for an explicit rollout. Deploying its
worker or migrations does not turn delivery on. Existing staging configuration
is preserved. Web and desktop push remain unsupported.

## Client and Apple configuration

Register a Firebase iOS app for `com.alialtaraif.field`. Its downloaded public
client values belong in the protected production build configuration:

- `PUSH_FIREBASE_API_KEY`
- `PUSH_FIREBASE_PROJECT_ID`
- `PUSH_FIREBASE_SENDER_ID`
- `PUSH_FIREBASE_IOS_APP_ID`
- `PUSH_FIREBASE_IOS_BUNDLE_ID=com.alialtaraif.field`

Android separately requires its production Firebase app ID and
`PUSH_FIREBASE_ANDROID_PACKAGE_ID=gg.fieldrush.app`. An iOS build does not need
the Android app ID, and vice versa. The client rejects missing platform
identities, wrong providers, sender/app-number mismatches, and the known staging
Firebase apps in a production build. Production never falls back to staging
Firebase identifiers. A shared Firebase project is possible, but its staging
and production app registrations must be distinct.

The Apple App ID, signed application, and provisioning profile must include
Push Notifications with the production APNs entitlement and the existing
Fieldrush Apple Pay merchant. The push build needs the remote-notification
background mode. Upload a production-topic APNs authentication key to Firebase
for this exact iOS app. Creating or uploading that credential is a separate
account operation; no credential is generated by these source changes.

Keep `PUSH_NOTIFICATIONS_ENABLED=false` until the client configuration and
backend are ready. In the production upload workflow, the corresponding switch
is `PRODUCTION_PUSH_NOTIFICATIONS_ENABLED`. Firebase messaging auto-init remains
off before the existing in-app opt-in and OS permission flow.

## Backend activation

Apply `20261027000800_production_push_dispatch.sql` through the protected
production deployment. The worker independently accepts only the exact pair
`FIELD_ENVIRONMENT=production` and
`SUPABASE_URL=https://zjsjuuhborxrlmdcpvlj.supabase.co`.

While delivery remains off, configure these server-only Edge Function secrets:

- `FIREBASE_SERVICE_ACCOUNT_JSON`: a dedicated account with send permission for
  the intended Firebase project; never bundle this JSON in mobile builds.
- `PUSH_WORKER_SECRET`: a strong, unique production worker credential, 32–512
  printable non-space ASCII characters.
- `PUSH_FIREBASE_PROJECT_ID`: the public Firebase project ID matching that
  service account. Production rejects a missing or mismatched value before
  contacting Google or claiming any delivery lease.

`PUSH_DELIVERY_ENABLED` remains `false` until activation is deliberate. Existing
server configuration supplies the production Supabase service credential; it
must never appear in mobile environment files.

Use a trusted service-role administration session on the exact production
project. Keep secrets as bound private parameters, not literals in saved SQL.
Configure the following in order:

1. Disable dispatch with `configure_push_dispatch(null,null,false)` and disable
   delivery through `configure_push_delivery` before changing environments.
2. Call `configure_push_dispatch_environment('production')`. The database pins
   future dispatch URLs to the exact Field Production endpoint. A change is
   rejected while either delivery switch is on; changing environments clears
   the old provider ID and endpoint without activating anything.
3. Explicitly configure the intended Firebase project using
   `configure_push_delivery(project_id,true)`.
4. Set the Edge runtime's `PUSH_DELIVERY_ENABLED=true`, then call
   `configure_push_dispatch(endpoint_url,worker_secret,true)` with
   `https://zjsjuuhborxrlmdcpvlj.supabase.co/functions/v1/fieldrush-push-dispatch`.
   This stores the worker credential only in Vault and preserves the existing
   cron schedule. A staging endpoint, another host, query, or trailing slash is
   rejected for production.

The database environment binding is an explicit administration choice because
hosted PostgreSQL does not expose the Supabase project identity as a reliable
database setting. It does not replace the worker's independent exact-project
runtime guard.

## Qualification and rollback

Verify one consented production TestFlight iPhone and the intended Android
release on real devices: foreground/background delivery, a receipt tap to the
correct account's Activity, denied permission, logout and another user's login,
and opt-out. Canonical server eligibility, recipient binding and preferences
still govern each send; a permission grant alone does not opt a different
account in. The worker accepts no caller-supplied recipient or message text.

Disable dispatch immediately with `configure_push_dispatch(null,null,false)`
and/or set `PUSH_DELIVERY_ENABLED=false` to stop new sends. Disabling does not
need a valid Firebase credential or retained Vault secret. Provider-accepted
messages cannot be recalled. Local tests prove configuration and authorization
contracts; they do not prove real APNs/FCM delivery or signing.
